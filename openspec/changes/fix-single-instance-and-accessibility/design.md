## Context

Honyaku is a menu-bar-only SwiftUI app (`LSUIElement`), not sandboxed. On launch it installs a session-wide CGEventTap on the Control key once Accessibility is granted (`HonyakuApp.startPipelineIfReady()` → `HotkeyService.start()`).

Current state:
- **No single-instance check.** Nothing stops a second process from starting. Xcode stops only the copy it launched itself, so copies started by `NSApplication.relaunch()`, by the login item, or from another path (for example `/Applications` versus DerivedData) keep running alongside it.
- **Ad-hoc Debug signing.** `project.yml` sets `CODE_SIGN_IDENTITY: "-"` and `DEVELOPMENT_TEAM: ""` for every configuration. The designated requirement becomes `cdhash H"…"`, so every rebuild invalidates the Accessibility grant. The onboarding checks `AXIsProcessTrusted()` every second, and it never turns true for a rebuilt binary.
- **`NSApplication.relaunch()`** (in `OnboardingView.swift`) runs `/usr/bin/open <bundlePath>` and then calls `terminate(nil)`. The process is still running at that point, so LaunchServices can just bring the existing process to the front instead of starting a new one.
- **Login item.** `registerLoginItemIfNeeded()` calls `SMAppService.mainApp.register()` on first run whatever the configuration, so a DerivedData Debug build can become the login item.
- **Project generation.** `Honyaku.xcodeproj` is generated by XcodeGen from `project.yml` and is checked in. The developer builds in Xcode; agents do not run `xcodebuild`.
- **Signing identities.** None are installed on the dev Mac yet. The developer will add an Apple ID in Xcode → Settings → Accounts.

## Goals / Non-Goals

**Goals:**
- At most one Honyaku process, and so at most one event tap, with the newest launch winning.
- "Quit & Relaunch" produces exactly one fresh process.
- The Accessibility grant survives Debug rebuilds once a team is configured.
- The project still builds for anyone without an Apple ID.
- Debug builds never auto-register a login item.

**Non-Goals:**
- Removing the "restart required" step from onboarding. Live detection already exists through polling. Whether a restart is truly needed can be revisited separately.
- Release signing, notarisation, the DMG, or CI. That is the separate, uncommitted v1.0.0 work.
- Cleaning up login items that earlier Debug builds already registered. This is a one-time manual step (see Migration Plan).

## Decisions

### 1. Single-instance enforcement: `SingleInstanceService`, newest wins

We add a small service in `Sources/Honyaku/Services/SingleInstanceService.swift`. At launch it:
1. Lists `NSRunningApplication.runningApplications(withBundleIdentifier:)` for the app's own bundle ID, excluding `ProcessInfo.processInfo.processIdentifier`.
2. Calls `terminate()` on each older instance. This sends a standard quit, so the older copy's `willTerminate` cleanup runs.
3. Waits for all of them to report `isTerminated`, checking asynchronously for up to 3 s, then calls `forceTerminate()` on any still running.

`startPipelineIfReady()` awaits this before calling `hotkeyService.start()`, so two event taps never overlap. The pipeline and UI still start straight away; only the tap is deferred. When no other instance is running, the step finishes immediately.

Only instances that launched *earlier* are terminated (compared by `launchDate`; if two copies launched at the same instant, the lower PID loses), so two copies launching together never quit each other. The check is off when the process is an XCTest host (`XCTestConfigurationFilePath` is set), because the unit tests run inside the app and a test run must not quit the developer's running copy.

The running-application lookup sits behind a protocol, following the existing `ServiceProtocols.swift` pattern. That lets unit tests cover the filtering and the escalation after the timeout without real processes.

*Alternatives considered:*
- **`LSMultipleInstancesProhibited` in `Info.plist`.** This only blocks second launches that go through LaunchServices, and it makes the *existing* copy win. That's the opposite of the chosen policy, and it would make Build & Run in Xcode exit silently.
- **Existing copy wins (activate it and exit).** Rejected by the developer: Build & Run must always run the fresh build.
- **A distributed notification or file lock.** More machinery than `NSRunningApplication` needs for the same result.

### 2. Relaunch: wait for exit, then `open -n`

We replace the body of `NSApplication.relaunch()`. It will start a detached `/bin/sh` that loops on `kill -0 <pid>` every 0.2 s until the current process has gone, then runs `/usr/bin/open -n <bundlePath>`. The PID and path are passed as positional arguments (`"$1"`, `"$2"`), not interpolated into the script string, so paths containing spaces or quotes are safe. After starting the shell, the app calls `terminate(nil)`. The child is reparented to launchd and outlives the app, which is fine because the app is not sandboxed.

*Alternatives considered:*
- **`NSWorkspace.openApplication(createsNewApplicationInstance: true)` before terminating.** This would also work, because the new copy's single-instance check would terminate the old one. But both processes would briefly run side by side. The spec asks for launch *after* exit, which is simpler to reason about.

### 3. Debug signing: an optional local xcconfig

In `project.yml`, the Debug configuration gets a `configFiles` entry pointing to a checked-in `Config/Debug.xcconfig`:

```
CODE_SIGN_STYLE = Manual
CODE_SIGN_IDENTITY = -
DEVELOPMENT_TEAM =
#include? "Local.xcconfig"
```

A developer who wants stable signing copies the checked-in `Config/Local.xcconfig.example` to `Config/Local.xcconfig`, which is listed in `.gitignore`:

```
CODE_SIGN_STYLE = Automatic
CODE_SIGN_IDENTITY = Apple Development
DEVELOPMENT_TEAM = <TEAMID>
```

The signing keys move from the target's `settings.base` into `settings.configs.Release`, with their values unchanged, because target-level build settings override xcconfig values. Release signing is therefore unaffected. `HonyakuTests` and `HonyakuIntegrationTests` use the same Debug xcconfig, because they are loaded into the app process as its test host: with hardened runtime on, a host signed by a team rejects an ad-hoc test bundle. `ENABLE_HARDENED_RUNTIME` stays on. Xcode adds `get-task-allow` automatically for development-signed Debug builds, so the debugger still attaches.

*Alternatives considered:*
- **Hard-coding the team ID in `project.yml`.** A team ID isn't secret, but this breaks the build for contributors without that team. It would also put personal account details in a public repo.
- **A self-signed local certificate.** The developer chose Apple Development instead. It's the standard route and reuses the same account needed for Developer ID.

### 4. Login item: skipped in Debug

`registerLoginItemIfNeeded()` returns early under `#if DEBUG`. The Settings toggle is left as it is, so a developer can still turn launch at login on by hand.

## Risks / Trade-offs

- **[Risk] The older copy is mid-recording when it's replaced.** Its in-flight audio is discarded. → Acceptable, since this only happens when a new copy is deliberately launched. The normal quit cleanup still removes temp audio and clears the pasteboard.
- **[Risk] `terminate()` may be ignored,** for example if the older copy is paused in the debugger. → Force-terminate after 3 s.
- **[Risk] A new copy launched from an older build path (for example `/Applications`) replaces a newer Debug copy.** → That is the literal "newest launch wins" policy, and it's what the developer asked for.
- **[Risk] Regenerating the xcodeproj also writes the uncommitted Release-signing hunk in `project.yml` into `project.pbxproj`.** → See Open Questions. The commit has to be sequenced with the release work.
- **[Trade-off] Without `Local.xcconfig`, Debug builds stay ad-hoc** and the grant is still lost on each rebuild. → Documented in the README, with the `tccutil reset` workaround.

## Migration Plan

1. The developer adds an Apple ID in Xcode → Settings → Accounts, then creates `Config/Local.xcconfig` with their team ID.
2. Regenerate the project (`xcodegen generate`), then build and run from Xcode.
3. One time only: remove the stale Honyaku entry in System Settings → Privacy & Security → Accessibility (or run `tccutil reset Accessibility com.honyaku.app`), then grant it again.
4. One time only: if an earlier Debug build was registered as a login item, remove it under System Settings → General → Login Items.

Rollback: revert the commit. Signing falls back to ad-hoc and the other behaviour returns to what it was.

## Open Questions

- **How to sequence this against the uncommitted release work.** `project.yml` already holds an unrelated, uncommitted Release-signing hunk. Regenerating the xcodeproj will pick it up. Either commit the release work first on its own branch, or stage only this change's hunks and regenerate the project after the release work lands.
